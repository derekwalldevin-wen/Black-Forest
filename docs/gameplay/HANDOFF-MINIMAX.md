## 游戏方向和体验目标

游戏定位：玩家穿越黑森林与山海异境，击败妖兽、获得妖契，把卡牌与妖兽的力量组合成自己的打法。

希望形成的体验链是：选择一个开局方向 → 在战斗中发现组合 → 根据牌组选择奖励 → 获得改变打法的妖契 → 应对有规则的异兽 → 进入山海境时发展已有构筑 → 想换一个组合再玩。

策划优先级：先验证不同打法，再验证组合成长，然后增加战斗挑战，最后扩展流程。每次交付应能单独运行和检查，避免所有系统同时改变后无法判断体验来自哪里。

## 阶段一任务一把传承定义成数据

传承只决定初始牌组，不附带额外属性、遗物、生命或资源加成。三套都为八张牌，全部取自现有 CARD_DEFS。

| ID | 显示名称 | 具体牌组 | 选择页说明 |
|---|---|---|---|
| `blood` | 猎血 | `strike ×3, defend ×3, blood_pact ×1, drain_life ×1` | 支付生命换取抽牌，用汲取恢复生命。 |
| `guard` | 守御 | `strike ×3, defend ×3, iron_wall ×1, riposte ×1` | 用格挡减少损失，利用反刺兼顾攻守。 |
| `talisman` | 符咒 | `strike ×2, defend ×3, fu_paper ×1, seal_gate ×1, xuan_ji ×1` | 灵韵驱动符箓，连续施法降低后续费用。 |

这三套是需要对比的原型配置，不是已经平衡的职业。猎血含一张罕见汲取，符咒使用独立资源，都可能强于守御；应在报告中记录实际差异，先不同时改动卡牌数值、敌人属性和奖励概率。

建议新增 `src/core/starters.js`，定义 `STARTER_DEFS` 和返回牌组副本的辅助函数。在 `index.html` 中按依赖加载。不得让不同新局共用同一个可变数组。

保留 `classic` 配置：四张劈砍、四张格挡。它服务旧存档、默认 API 调用和对比测试，第一阶段不必新增第四个正常菜单选项。

建议接口：`RUN.newRun(starterId)`。无参数继续使用 classic；正常新游戏的确认按钮显式传入三种 ID 之一。不得悄悄改变已有调试和测试对无参数调用的预期。

## 阶段一任务二统一新游戏入口

建议在标题场景内做传承选择面板，复用现有遮罩与按钮，无需创建新场景。

| 触发位置 | 规定行为 |
|---|---|
| 无有效存档时开始游戏 | 打开传承选择，查看介绍与八张牌概览，确认后创建新局 |
| 有有效存档时继续 | 加载原局；不询问传承，不替换已有牌组 |
| 有存档时重新开始 | 沿用现有覆盖进度确认，确认后进入传承选择 |
| 战败后重开 | 返回传承选择入口，不直接套用无参数 newRun 开始战斗 |
| 通关后再玩 | 返回传承选择入口，允许换另一套打法 |
| 取消传承选择 | 返回标题；选中、查看或取消选项均不写入新存档 |

检查标题、失败结算、通关结算里所有 `RUN.newRun()` 调用，处理它们各自的入口语义。不要只在标题页添加按钮而漏掉重开路径。

只有确认开局时才创建 RUN 并保存。先标记正在启动，再执行创建、保存和场景跳转。双击、Enter 连按和触屏点击不得生成多局或重复启动场景。选择面板显示时，底部按钮和标题快捷键不能穿透触发。

选择页先复用现有卡面、图标和面板。介绍只说明当前确实存在的功能，不宣传妖契、保留格挡或反击爆发。面板在 390×844 与 540×960 视口下应能读清和完成选择。

## 阶段一任务三让资源和说明匹配牌组

灵韵资源的显示条件建议为：当前为山海境，或者 RUN.deck 中至少有一张牌的费用类型为 spirit。

按整副牌组判断，不能仅按当前手牌判断。符箓进入弃牌堆后，资源栏也应继续显示。森林下使用现有哥特色板与面板，标签可回退为“灵韵”；不改变境域主题来解决资源显示。

保留每回合自然恢复 1、默认上限 3、跨回合积累、共鸣回合清零和费用最低为 0 等已有规则，不另给符咒传承开场资源奖励。

选择页和帮助页必须说明：行动力用于普通牌；灵韵用于符箓；本回合先打符箓会降低后续符箓费用。修改原有“第四章起才使用”的说明，使它能解释符咒传承。

在灰狼调试战斗中设置手牌为 `xuan_ji, seal_gate, fu_paper, strike, defend`，其他加成为空。第一回合自然获得 1 灵韵后，依次打玄玑、封门、符纸，应能看到灵韵恢复、后续费用降到 0、共鸣增长；随后劈砍仍消耗行动力。下一回合共鸣归零，灵韵按原规则恢复。这是规则演示，不是平衡结果。

验证用固定手牌只在调试或测试路径生效，不得改变正常洗牌与随机奖励。

## 阶段一任务四兼容旧档并保持续玩含义

本阶段只新增已使用的存档字段：`schemaVersion: 1`、`starterId`。若接手时已有版本体系，沿用其版本策略并记录实际版本号。

旧档缺少 starterId 时补为 classic，保留其现有牌组、血量、金币、遗物和章节。classic 是兼容标识，不是要求把成长后的牌组重置为八张基础牌。已经选过传承的新档必须保留原 starterId 和成长后的牌组。

有效旧档应能继续；无效或无法解析的存档应走明确的新游戏路径，不能因为 hasSave 仅检查字符串存在就显示可继续却无法启动。加载仅恢复允许的状态字段，避免序列化数据覆盖 RUN 的方法。

存档依然采用当前 RUN 进度粒度。本阶段不增加完整战斗快照、随机数种子体系、路线字段和妖契字段。以后需要这些字段时，由对应阶段增加迁移。

## 阶段一验收标准

技术通过与体验通过分开判断。

### 逻辑检查

- 三种配置均为八张有效卡，份数与任务书一致；不同新局的牌组互不影响。
- 无参数 newRun 仍得到 classic；三个显式传承 ID 分别得到对应初始牌组。
- 旧档迁移保留非基础牌、血量、金币、遗物和进度；加载新档不重置成长牌组。
- 森林基础牌组隐藏灵韵、森林符咒牌组显示灵韵、山海牌组显示灵韵；符箓不在手中时显示不闪退。
- 已有逻辑测试继续通过，新增有效断言；不以固定总数要求删除或跳过测试。

### 浏览器检查

- 三套均可从正常入口选择并进入战斗；继续存档不重新选传承。
- 选择、取消、重复点击、键盘确认、重开与再玩路径行为正确。
- 战斗能出牌、结束回合、击杀、进入奖励、选择或跳过、推进下一场；击杀与奖励仅结算一次。
- 玄玑、封门、符纸的规则演示符合上文约定，费用与资源显示同步。
- 两种视口下选项、手牌、资源栏和结束回合按钮可读且不互相遮挡；无新增控制台错误或素材加载失败。
- 检查森林和山海显示、九张手牌、奖励、事件、`?art=off` 的相关回归。模拟触屏与真机触屏结果分开记录。

### 体验观察

先用三套传承分别实际游玩前三战，各至少两轮，记录六次具体结果。由 MINIMAX 操作或自动策略产生的结果必须注明，不称为真实玩家测试。普通玩家试玩有条件时再补充，不能替用户编造反馈。

记录：到达哪一战、每战回合数、主要生命损失、关键牌如何使用、奖励选择和原因，以及是否出现有效或无效的策略选择。胜率、通关时间和三个配置的强弱先观察，不预设它们已经平衡。

重点回答三个问题：猎血是否需要考虑何时付血与汲取；守御是否需要考虑格挡与伤害分配；符咒是否需要考虑出牌顺序。如果某套只让人重复一种固定动作，或森林奖励让符咒无法成长，应在报告中如实提出，由验收后的设计决定怎样修正。

技术通过但没有玩家试玩时，可以交付为“功能完成，体验待验证”；不要写为“玩法已受欢迎”。

## Codex 的验收和下一阶段决策

验收按以下顺序进行：读取报告和实际代码 → 重跑适当逻辑检查 → 操作正常入口与关键边界 → 对比三种打法 → 判断是否有阻断或明显体验问题 → 给出下一份有明确范围的实施任务。

若开局差异成立，阶段二再选一个妖契做完整原型，包括早期获取、装备、规则触发和反馈。相柳契、祸斗契、饕餮契为候选；选择应依据当前牌组是否能展示它、组合收益和实现成本。饕餮需要本场移除区，通常比单一被动触发复杂，不预先要求三个同时完成。

若开局差异不成立，先调整牌组或说明；若某种资源明显失衡，先分析原因。不要同时增加妖契、敌人机制和路线来掩盖当前问题。

后续路线与铸坊先试一个章节；异兽先试一个规则；过境升契在组合已经形成后加入。独立六战实验流程留到对应阶段再设计，第一阶段不改十八战流程。
