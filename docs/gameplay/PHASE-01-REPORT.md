## 1. 阶段一完成了什么

### 任务一 · 三套传承 + classic 兼容配置

新增 `src/core/starters.js`（77 行）。四套配置全部取自现有 `CARD_DEFS`，**没有新增任何卡牌或效果算子**：

| id | 名称 | 八张牌 |
|----|------|--------|
| `blood` | 猎血 | 劈砍×3、格挡×3、血契、汲取 |
| `guard` | 守御 | 劈砍×3、格挡×3、铁壁、反刺 |
| `talisman` | 符咒 | 劈砍×2、格挡×3、符纸、封门、玄玑 |
| `classic` | 经典 | 劈砍×4、格挡×4（`legacy: true`，不进正常菜单） |

设计边界：**传承只决定初始牌组**，不附带属性、遗物、生命或资源加成。
`classic` 只服务旧存档、默认 API 调用和对比测试，不作为菜单里的第四个选项。
`starterDeck()` 返回副本，避免第二局牌组被第一局的 `addCard` 污染。

### 任务二 · 统一新游戏入口

标题页新增传承选择面板（depth 70 遮罩 + 三行 + 资源图例 + 确认/取消，支持键盘 1/2/3 + Enter + Esc）。

入口分流语义：

| 入口 | 行为 |
|------|------|
| 无存档 · 开始征途 | → 传承选择 → 确认后才建 RUN |
| 有有效存档 · 继续征途 | → 直接进战斗，**不问传承** |
| 有存档 · 重新开始 | → 二次确认 → 清档 → 传承选择 |
| 战败 · 重头来过 | → 清档 → 传承选择 |
| 通关 · 再走一次 | → 清档 → 传承选择 |
| 存档损坏 | 标题退回「开始征途」，Enter 仍能进传承选择，不会卡死 |

只有「确认」才建 RUN 并写存档；选中、查看、取消都不写。

### 任务三 · 灵韵按整副牌组判定

`CombatScene.refreshEnergy()` 的显示条件从 `!!THEME.spiritLabel` 改为 `RUN.showSpiritMeter()`：

```
realm() === 'shanhai'  ||  deckUsesSpirit(RUN.deck)
```

按**整副牌组**而不是当前手牌判断——符箓可能全在弃牌堆里，此时资源栏必须仍在，否则玩家看着灵韵凭空消失。
选择面板与帮助页同步说明「行动力 / 灵韵 / 共鸣」三条规则。

### 任务四 · 存档 schemaVersion / starterId / 旧档迁移

- 新增 `RUN_SCHEMA_VERSION = 1`
- 存档改为**白名单**写出（`SAVE_FIELDS`），排除 `_forcedEnemy` / `_dbgDeck` 这类调试暂存字段
- 新增 `RUN.starterId`
- 旧档（无 `starterId` / 无 `schemaVersion`）加载时补成 `classic` 并**回写磁盘**；玩家已构筑的牌组原样保留
- `hasSave()` 与 `load()` 共用 `_readSave()`，判定完全一致

## 3. 修复的问题

### 3.1 阶段一自身引入并修掉的

| # | 问题 | 影响 |
|---|------|------|
| 1 | `TitleScene` 类方法后多了逗号（4 处 `},`） | **整个文件无法解析**，页面直接白屏。class body 不允许尾逗号（对象字面量可以） |
| 2 | 数字键分支 `parseInt(exec() 返回的数组)` | `/^(?:Digit\|Numpad)([1-9])$/.exec('Digit2')` 返回数组，被拼成 `'Digit2,2'` 解析成 `NaN`，`i < 长度` 恒假——**面板上的 1/2/3 永远选不中传承** |
| 3 | `closeStarterPicker()` 不复位 `_starterPicker` | 取消一次之后，标题页再也开不了新的一局 |
| 4 | 从 `scene.settings.openStarter` 读场景数据 | Phaser 把它放在 `scene.settings.data`，读错一层永远是 `undefined`——**战败/通关回到标题后传承面板从来没弹出来过** |
| 5 | `create()` 不复位 `_starting` | Phaser 复用场景实例，上一次留下的 `true` 会让 `startRun()` 第一行就 return，**标题页永久失效** |
| 6 | 旧档迁移只改内存不回写磁盘 | 玩家开一次标题页就退出，磁盘上还是旧格式 |
| 7 | 战败浮层 depth 70 + 战斗结束时手牌仍吃指针 | 结算面板与 depth 200+i 的手牌抢同一块屏幕 |

### 3.2 阶段一**之前就存在**的缺陷（本轮摸底时挖出来的 P0）

这几条都在 `backup-phase0/` 的改动前副本里逐条核对过，确认**不是本轮引入的回归**。

| # | 位置 | 现象 | 严重度 |
|---|------|------|--------|
| A | `CombatScene._ended` 从不复位 | 走完 战斗→奖励→**事件**→再进战斗，第二场击杀时 `victory()` 第一行 `if (this._ended) return`，`state.busy` 永远为 true，**敌人死了也不进奖励页，玩家被软锁** | **P0** |
| B | `RewardScene._picked` 从不复位 | 第二张奖励页 `pickCard/skipCard` 直接 return，**从第二场战斗开始必然卡在「挑选一张卡牌」** | **P0** |
| C | `EventScene._picked` 从不复位 | 第二个事件节点起卡死 | **P0** |
| D | `RewardScene.relicLayer` 从未赋值 | `showRelicChoice()` 建了容器 `c` 却没存回去。键盘选遗物传的是 `null`，`pickRelic` 里的补间抛错、`enableContinue()` 不执行——**键盘玩家在遗物页永久卡死** | **P0（键盘路径）** |
| E | `RewardScene._ending` 从不复位 | 看过通关画面之后，本局再开任何奖励页都会被判定成已通关 | 高 |
| F | `RUN.hasSave()` 只检查字符串存在 | 损坏 JSON / `started:false` / 空牌组都会让「继续」亮着却点不动 | 高 |
| G | `_forcedEnemy` / `_dbgDeck` 被序列化进存档 | 用 `?debug&enemy=` 调过一次平衡，之后每一局真实游戏都打同一个敌人 | 中 |

> **A–G 的共同根因是同一类**：Phaser 复用场景实例，而一次性闸门只在 `create()` 之外复位。
> 第一场永远正常，所以这类问题极易漏过——阶段零的摸底也只走到「事件之后能回到 Combat」为止，
> 没有继续往下打，才没暴露 A。

为此新增了两道防线：

1. `tools/test-logic.js` 的 **`[一次性闸门复位]`** 分节：全场景扫描所有「只置 true」的实例字段，
   要求每个都能在 `create()` 里找到复位（14 条断言）。
2. 回归断言把 A–G 各自的触发条件钉在源码上。

### 3.3 顺手修掉的连带问题

- `tools/simulate.js` 未加载 `starters.js`，被 `run.js` 的改动打断（`ReferenceError: starterDef is not defined`）。
- `tools/verify-scenes.js` 里「标题页 Enter 直接开打」的旧断言已不成立，改为「Enter → 面板 → Enter → 战斗」。

## 7. 体验观察 · 六次前三战记录

> **操作主体：MINIMAX 的贪心自动策略，不是真人玩家。**
> 策略：能打就打，按「伤害 / 格挡×0.75 / 抽牌×5 / 灵韵×8 / 回血×10 / 血契扣血×−2」打分；
> 血量低于 55% 时给回血类加权。操作全部走**真实键盘通路**（1~9 出牌、Space 结束回合、
> 数字键与 Enter 走奖励页和事件页），不是直接调场景方法。
> 因此这些记录只能说明「这套牌组在自动基准策略下能不能打通前三战」，**不能代表真人体验**。

| 传承 | 轮次 | 第1战 wolf | 第2战 mushroom | 第3战 alpha_wolf |
|------|------|-----------|----------------|------------------|
| 猎血 | 1 | 胜 · 2 回合 · 70→70 | 胜 · 2 回合 · 70→70 | 胜 · 3 回合 · 70→70 |
| 猎血 | 2 | 胜 · 2 回合 · 70→70 | 胜 · 2 回合 · 70→70 | 胜 · 4 回合 · 70→70 |
| 守御 | 1 | 胜 · 3 回合 · 70→70 | 胜 · 2 回合 · 70→70 | 胜 · 5 回合 · 70→70 |
| 守御 | 2 | 胜 · 2 回合 · 70→70 | 胜 · 5 回合 · 70→70 | 胜 · 4 回合 · 70→70 |
| 符咒 | 1 | 胜 · 3 回合 · 70→70 | 胜 · 3 回合 · 70→70 | 胜 · 6 回合 · 70→70 |
| 符咒 | 2 | 胜 · 3 回合 · 70→70 | 胜 · 2 回合 · 70→70 | 胜 · 4 回合 · 70→70 |

**本轮 18 战 18 胜**（另一次独立运行是 17/18，守御第 1 轮在第 3 战阵亡）。
每轮都完整走完了 战 → 奖励（三段式：选牌 → 选遗物 → 继续）→ 事件 → 下一战。

能从数据里读出来的（不是编造的玩家反馈）：

1. **前三战对三套牌组几乎没有区分度。** 本轮 18 场战斗**全部生命 70→70，一滴血没掉**。
   第 1 战（wolf）三套都在 2~3 回合内结束。
2. **难度几乎全压在第 3 战 alpha_wolf。** 它的平均战斗回合数（3~6）明显高于第 1、2 战（2~3），
   另一次运行里唯一的阵亡也发生在这里。前两战对玩家几乎没有压力。
3. **回合数差异主要来自抽牌方差，不是牌组强度。** 同一传承两轮之间
   守御第 2 战出现 2 回合 vs 5 回合、符咒第 3 战出现 6 回合 vs 4 回合这种量级的抖动；
   三套传承之间的平均回合数差异并不稳定。
4. **符咒在森林里能跑通**，灵韵栏正常出现、共鸣连打生效——但同样 6 场全胜无伤，
   说明森林阶段对灵韵机制的压力测试等于零。
5. 战后恢复（26% / 42%）在这三战里**一次都没用上**（血量没掉），
   18 战流程的复利问题在前三战观察不出来。

**技术通过，体验待验证。** 没有真人试玩，不能写「玩法已受欢迎」。

## 10. 调整建议（最多三条）

### 1. 把「场景复用 + 一次性闸门复位」当成硬规则，现在才有测试兜住

**证据**：3.2 里的 A、B、C、D、E 五条全部是同一类，且全部在**第一场之后**才发作；
阶段零摸底走到「事件之后能回到 Combat」为止，正好没踩到 A。
`test-logic.js` 新增的 `[一次性闸门复位]` 分节（14 条，全场景扫描）才把它们一次性找出来。

**建议**：此后任何在场景里新增的 `this._xxx = true` 闸门，都必须能被这个扫描捕获；
每阶段的验收清单固定要求**至少连续跑通两场战斗并跨过一次事件节点**。

### 2. 阶段二先补「牌组之外的一处规则差异」，再谈平衡

**证据**：六次记录里本轮 18 战全部生命 70→70，三套传承在前三战的通关节奏几乎一致
（第 1 战都是 2~3 回合），差异主要来自抽牌方差而非牌组强度——
同一传承两轮之间就出现 2 回合 vs 5 回合的抖动。
换句话说，现在三套传承的差别只是「抽到什么牌」，不是「怎么打」。

**建议**：阶段二先给每套传承一处明确的规则身份（例如猎血的付血要计入某个代价、
守御的格挡能触发反击窗口、符咒的共鸣跨回合保留），
否则平衡数值调出来的差异会被抽牌方差淹没，调了也看不出效果。

### 3. 选择/结算类界面的可点性需要真机验收，不能只看截图

**证据**：Playwright 合成指针对战败按钮 4 次全未命中，而同一场景「结束回合」按钮正常；
按钮命中区经逐点计算是正确的（本地坐标 `(0,-40)` 落在 `[-200,-55,400,110]` 内），
把浮层 depth 从 70 抬到 300、以及战斗结束时关掉手牌输入，都**没能**让合成点击稳定生效。
说明这类问题在自动化环境里既可能被误判成 bug、也可能被漏掉。

**建议**：把「两视口 + 真机触摸点按」列进每阶段的硬性验收项，
特别是所有 `makeButton` 生成的按钮——合成环境通过不代表手指点得动。
