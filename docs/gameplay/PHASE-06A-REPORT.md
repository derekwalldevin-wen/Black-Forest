## 2. 修正了哪些差异

### 2.1 状态来源：RUN 成为唯一权威

旧版 `runGame` 自己持有局部 `deck` / `relics`，而事件效果写的是 `RUN.deck` / `RUN.relics`。
两套数据不是同一份，**事件拿到的牌和遗物根本没进后续战斗**。

现在战斗直接读 `RUN.deck` / `RUN.relics` / `RUN.maxHp` / `RUN.gold`，
事件效果改的就是下一场战斗读的那一份。

任务书里的只读复现已验证消失：seed=1 的符咒局打到第 18 战时，
模拟牌组与 `RUN.deck` 一致、遗物与 `RUN.relics` 一致。

### 2.2 结算顺序：照抄 CombatScene

| 环节 | 旧模拟器 | 实战 | 现状 |

| 敌方回合 | 敌人先行动 → 再结算状态 | **先结算状态** → 敌人再行动 | 已改为先结算 |

### 2.4 独立外生随机流 —— **6A 初版没做到，验收时才发现**

这一条初版声称已完成，**实际是错的**，第 7 节的补测把它揪了出来。

`spawnEnemy` 的签名是 `spawnEnemy(id, index)`，第二个形参是**实例序号**，
不是随机源；它内部直接调 `Math.random()`：

```js
function spawnEnemy(id, index) {
  const d = ENEMY_DEFS[id];
  const hpMax = d.hp[0] + Math.floor(Math.random() * (d.hp[1] - d.hp[0] + 1));
```

初版写了 `const r = exo(seed,'enemyHp',g); spawnEnemy(enemyId, r);`——
**流算出来了，但根本没接进去**。敌人血量仍然跟着内生流跑。

后果很直接：三套构筑出的牌数不同 → 洗牌次数不同 → 敌人血量序列整体错位。
实测同一 seed 下：

```
blood     0:27 1:22 2:58 3:32 4:35 5:60 6:26 7:58 8:76
guard     0:27 1:25 2:56 3:31 4:34 5:58 6:27 7:58 8:76   ← 第 1 战起就不一样
```

也就是说我此前所有的 A/B 数字，**两组之间并没有真正配对**。
修法是用 `withRng` 在调用期间替换 `SEEDED_MATH.random`，三套构筑的序列才一致：

```
blood / guard / talisman  0:30 1:26 2:58 3:34 4:37 5:62 6:30 7:58 8:83
```

**这一条现在有自检守着**（`ab-test --selftest` 第 5/6 项），
以后再改坏了会直接失败。

### 2.5 意图刻意**不**外生化

同一次修正里我把 `rollIntent` 也接上了外生流，结果 200 局里有 **28 局触发回合上限**
（修复前是 0）。

原因是意图是**对当前局面的响应**：血量比例不同就该出不同招式。
按 `(种子, 战次, 回合)` 钉死，等于把「防御+治疗」型敌人的招式锁成一条固定循环，
凭空制造僵局。任务书第 4 项要求的是「下一场**敌人血量和奖励**的随机位置」不被挪走，
意图不在其中，且书里明确写着「状态改变导致敌人阶段或候选池不同是合法响应」。

所以意图留在内生流，并加了断言禁止把它外生化。

旧版在胜利后按 88% 概率塞一张牌、每两战塞一件遗物——这是模拟器自造的规则。
现在按 `RewardScene` 的真实结构：卡牌三选一、遗物按 `boss || step % 2 === 1` 出现、
金币按 `CombatScene.victory` 的公式结算、付费选项先查余额。

### 4.1 补齐这 5 个用例时，又抓出**两个真的模拟器 bug**

这两条不是对照台的问题，是模拟器算错了，而且都直接踩在 6B 要动的杠杆上。

**Bug A · 模拟器没有「付不起就不许出牌」的校验。**
实战 `CombatScene.playCard` 有一道提交校验：

```js
const payable  = effectiveCost(d, S.resonance);
const available = cardCostType(d) === 'spirit' ? S.spirit : S.energy;
if (payable > available) { card.deny(); return false; }
```

模拟器原来直接出牌。于是「打出一张付不起的牌」在两边结果不同：
**实战扣血，模拟器照样结算**。
`damage_times` 用例就是被这一条揪出来的（九首诀 2 灵韵，开局只有 1 灵韵）。

**Bug B · `resonanceDamage`（雷旨）漏掉了基础那一击。**
真实游戏是「基础 6 点 **加上** 每层共鸣各 6 点」：

```js
this.hitEnemy(eff.v, { talisman: tal });          // 基础
for (let i = 0; i < S.resonance; i++) { ... }    // 每层共鸣
```

模拟器只循环共鸣、把基础那一击漏了。共鸣 2 层时实战 18 点、模拟 12 点——
**共鸣伤害类卡牌被系统性低估**。

这条对 6B 特别重要：设计决策里「共鸣减费下限改为 1」正是要动的杠杆，
而模拟器此前对共鸣类卡牌的算力就是错的。**如果不做这次对齐，
6B 会用一把偏短的尺子去量候选参数。**

两处都已修复，并补进 `test-logic.js` 防回归。

### 4.2 为什么第一版跑出来是「2 通过 / 7 不一致」

对照台自己有三个未受控变量，每一个都会让后面的比较全部失真。
**这三个都不是模拟器的问题，是尺子的问题**：

1. **敌人 `hpMax` 两端各摇各的。**
   `spawnEnemy` 是 `hp[0] + floor(random * 区间)`，模拟器走种子、实战走原生
   `Math.random()`，于是第 0 步就是 `模拟 28 / 实战 30`。
   修法：`hp` 与 `hpMax` 一起钉成常量 40。
2. **敌人意图两端各摇各的。**
   `rollIntent` 同理。修法：每个用例显式给出该步的意图。
3. **读状态早于结算结束。**
   实战的敌方回合是链式的（`endTurn` 等 620ms → `runEnemyTurn` →
   每个行动间隔 780ms → 收尾再延时 → `startPlayerTurn` 再等 160ms 清 busy）；
   而共鸣伤害在 `CombatScene` 里是 `delayedCall(160 + i*160)` 逐次补刀，
   **这些补刀期间 `busy` 不会被置起**，只等「不忙」不够。
   修法：轮询到「不忙」**并且**给一个硬下限。

另外两处对照台自身的问题：

4. `cs.startCombat()` 会自己在 420ms 后再跑一次 `startPlayerTurn`，
   把刚固定好的手牌换成一次随机抽牌。修法：注入后先等它自己跑完，再钉状态。
5. 手牌应当按**多重集**比对，不比顺序——弃牌堆洗回抽牌堆时两边各摇一次，
   顺序天然不同，「手里有哪些牌」才是战斗输入。

### 4.3 补「付费选择」用例时，抓出一个**游戏侧**缺陷

铸坊的「淬火」原本把费用写成 gold 负值：

```js
effects: [{ op: 'gold', v: -70 }, { op: 'card', rarity: 'rare' }]
```

但 `EventScene.buildChoices` / `pick` **只认 `choice.cost`**：

```js
const affordable = !c.cost || RUN.gold >= c.cost;      // 没有 cost → 一律「付得起」
if (c.cost && RUN.gold < c.cost) return;                // 没有 cost → 不拦
```

于是这一项**根本不收费**，而 `applyEventEffects` 里 `RUN.gold = Math.max(0, RUN.gold + v)`
会把金币直接夹到 0——**钱不够也能白拿一张罕见牌**。

修法：改成 `cost: 70`（与「买遗物」「删一张牌」两个已有付费选项同一套写法），
费用交给 `EventScene.pick` 扣。同时把模拟器的付费判定也改成读 `choice.cost`，
原先它是从 effects 里找 gold 负值推断的，与实战分叉。

这是一条**游戏侧缺陷**，由 6A 的对齐工作发现，不属于 6A 授权的「只测量不改动数值」范围，
但它属于「阻断对照的问题」，故按授权修掉并单列证据。

### 4.4 对齐时发现的第三个模拟器 bug：**开场回复遗物在本场失效**

`combatHealPct`（骨髓药瓶「每场战斗开始时，回复 10% 生命上限」）：

| | 写入 | 结果 |
|---|------|------|
| 实战 `CombatScene.startCombat` → `healPlayer(amt)` | `P.hp` **和** `RUN.hp` | 50/70 → **57/70**，本场就回上 |
| 模拟器（修复前） | 只写 `RUN.hp` | 战斗内仍是 50，回复被丢在本场之外 |

也就是说这条差异**一直在**，只是方向被我判反了：不是遗物坏了，是**尺子坏了**。
影响不只是这一个遗物——凡是靠 `combatHealPct` 拉高起始血量的构筑，
在模拟器里都被少算了一次回复，通关率被系统性低估。

已按 `healPlayer` 的口径修好（同时写 `S.player.hp` 与 `RUN.hp`），
并加了 `combat_heal_relic` 对照用例把它钉住，防止再退回去。

> 这条也说明 3.2 那个判断为什么错：我当时看到差异现象，
> 就直接把它归给了**看起来更像"漏写"的那一边**，
> 没有先确认两边各自的实际调用。

## 4.5 跨场景用例（状态跨场景传递的边界）

战斗内的 14 个用例都在同一场战斗里比对。任务书另外点了三项跨场景的，
形状不同——不在战斗内部，而在**状态跨场景传递**的边界上，
所以对照台单开一段 `CROSS`。

| 用例 | 验证内容 | 结果 |
|------|---------|------|
| `event_reward_next_fight` | 事件拿到的一张牌与一件遗物，下一场战斗**真的用上** | 通过 |
| `ascend_refresh` | 第一次进第四章触发升契仪式；刷新后**不重复触发** | 通过 |
| `ascend_branches` | 升契仪式**三条分支各自**的效果差异 | 通过 |
| `event_remove_card` | 删牌选牌界面：默认选中 / 光标移动 / 翻页 / 每次只移除一张 | 通过 |
| 付费选择 | 见 4.3 | 通过（并抓出缺陷） |

`event_reward_next_fight` 的断言方式值得记一笔：第一版断言的是
「战斗里的格挡 = 6」，结果两边都是 0——因为 `startPlayerTurn` 开头会把
block 清零，**断言等于空转，两边一致并不代表遗物生效**。
改成断言 `S.mods.startBlock`（遗物的 mods 有没有进到战斗状态）之后，
两边都是 6，这才真正证明了传递。

`ascend_refresh` 没有模拟器对照：升契是**场景路由**
（`CombatScene.create` 直接 `scene.start('Event')`），不是数值算子，
所以直接断言两次刷新的预期结果：第一次 `id=ascend_rites` 且 `ascended=true`，
递交后妖契升阶为 `huodou_yu`，第二次刷新直接进战斗、不再进仪式。

`ascend_branches` 补的是同一条仪式的**另外两条分支**。只测「递交」是不够的——
仪式里另外两个选项的效果差异同样需要验证，否则其中一条写坏了不会被发现：

| 分支 | 契约 | 牌组 | 遗物 | 生命 |
|------|------|------|------|------|
| 1 递契 | `huodou_yu`（升阶） | 10（+1） | 0 | 40（不变） |
| 2 只取火 | `huodou`（不变） | 9（不变） | 1（+1） | 61（+30% 上限） |
| 3 转身走 | `huodou`（不变） | 9（不变） | 0 | 40（不变） |

`event_remove_card` 补的是模拟器**根本走不到**的那部分：它只会「弃第一张」，
而真实界面把重复牌合并成 `_groups`、每页 12 组、还带光标和翻页。
所以这条同时验了三件事——模拟器的默认策略与界面默认选中是否一致、
另外两条路径真的能选中别的东西、以及**重复牌合并后每次只移除一张**
（否则点一张 `strike×3` 会一次扣掉三张）。

| 操作 | 选中 | 移除张数 |

### 4.6.1 多遗物在同一 mods 键上的叠加

现有 13 件遗物里**没有任何两件共用一个键**，所以 `t[k] = (t[k]||0) + m[k]` 这条路径

### 4.6.2 「转身走」之后是否重复触发升契

`ascended` 是在 `CombatScene.create` 路由到仪式**之前**就置位的，

若这条将来失守，表现会是玩家每打一场就被仪式拦一次。

## 5. 第 7 项：自检加强

旧的自检只证明「同一个程序可重复」，证明不了「配对环境是对齐的」——
两臂若用了不同的随机流，跑出来的差异照样可以全是噪声，而旧自检照样通过。

现在七项（`node tools/ab-test.js --selftest`）：

```
通过  同种子重复运行
通过  相同配置的两个臂
通过  deckOverride 等于 classic
通过  外生流不受内生流消耗影响
通过  同种子换构筑：敌人血量序列一致（blood vs guard）
通过  同种子换构筑：敌人血量序列一致（blood vs talisman）
通过  敌人血量序列样本不足，配对前提未被真正验证
```

第四条是外生流独立性的证据：故意多消耗 37 次内生流，
外生流（敌人血量、奖励卡）取值逐位不变。

**第五、六条是补测时才加的**，也是最有价值的两条——
它们抓到「敌人血量其实一直走内生流」这个缺陷（见 2.4）。
在此之前，「配对 A/B」只是**构造上看起来成立**，从未被验证过：
三套构筑出的牌数不同、洗牌次数不同，敌人血量序列从第 1 战起就分叉。

第七条是一条反向断言：万一样本量被改小到不足以暴露差异，
「一致」会因为两边都没打而成立，那自检就白做了。

### 6.3 统计口径：不再用「相差 5 个百分点就是噪声」

任务书第 6B 节明确要求「报告比例的 95% 区间、配对差值与翻转，
**不再使用「固定相差 5 个百分点就是噪声」的判读**」。
早期版本的 `ab-test.js` 就是拿 5pp 当门槛——那种判读既不知道样本量、
也不知道方差，在 300 局和 3000 局上是同一句话。

现在改为：

- **Wilson 得分区间**（低比例下比正态近似稳）给每个比例的 95% 区间；
- **McNemar 精确配对检验**看同一批种子下两臂的翻转；
- 区间是否重叠，与配对检验是否显著，**分开陈述**；
- 支持 `--batch` / `--seed-base` 跑**未参与选参数的独立种子批次**，并把批次号打印出来。

> 这也解释了为什么「区间有重叠但 McNemar 显著」会同时出现：
> 前者说的是**独立抽样**下点估计的可分性，后者利用了**配对结构**。
> 两个都报出来，才是完整的证据。

### 6.5 一条必须纠正的旧结论

消融实验说「玄玑解释约三分之一，符纸+封门解释三分之二」。
**在真正配对的模型上，结论更极端**：

| 臂 | 通关 | 过哥特 |
|----|------|--------|
| 符咒原样 | 48.0% [42.4,53.6] | 86.0% [81.6,89.5] |
| 玄玑 → 格挡 | **51.0%** [45.4,56.6] | **88.0%** [83.8,91.2] |
| 去掉全部符箓 | 41.0% [35.6,46.6] | 80.7% [75.8,84.7] |

**拿掉玄玑之后符咒反而略微变强**（48.0% → 51.0%，配对 p=0.0002）。
玄玑在当前规则下对通关率的贡献是**中性偏负**的，
全部约 10pp 差距来自符纸 + 封门这一对。

对 6B 的直接含义：

- 「玄玑改 1 行动力技能」这条杠杆**不用做**，它改不动通关率；
- 真正有效的是「基础符箓收益 6/6」与「正费用符箓最低费用 1」这两条；
- 这与设计决策文件里「玄玑的决策诱因本身尚不足」的判断方向一致，
  但**原因不同**：不是缺少前瞻 AI，而是**玄玑这张牌本身就不构成取舍**。

### 6.6 独立种子批次确认（6B 协议的前置验证）

任务书要求「用**未参与选参数**的独立种子批次，每臂至少 1000 局确认选中的候选」。
`ab-test.js` 现在支持 `--batch` / `--seed-base`。用一批独立种子跑基线，
确认上面那些差距不是选参批次的产物：

| 臂 | 通关 [95% 区间] | 过哥特 [95% 区间] |

| blood+契 | 36.7% [32.9,40.6] | 83.3% [80.1,86.1] |
| guard+契 | 32.8% [29.2,36.7] | 77.3% [73.8,80.5] |
