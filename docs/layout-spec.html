竖屏卡牌手游
布局规范与竞品结论

对标《杀戮尖塔》系统深度 +《月圆之夜》竖屏体验。核心结论：不能靠「把横屏 UI 压扁」，必须改规则 + 按拇指区重新设计。

三个决定性事实

调研指向同一个方向：竖屏不是「横屏的窄版」，而是一套需要重新做取舍的设计。

已验证

月圆之夜改了规则

把 StS 的「能量 3 + 多敌人」改成「行动力 + 1V1」。这一改把横向空间需求砍掉一半，卡牌文字才塞得下。

踩坑警告

StS 手机版被差评

评测共识：UI 小得像蚂蚁、误触出牌毁掉 40 分钟的局、上滑手势和 iOS 切 App 冲突、建议买平板。

硬约束

拇指区决定生死

49% 用户单手持机，60%+ 触摸发生在下半屏。竖屏的真正优势是「底部空间天然充裕」—— 这才是选竖屏的根本原因。

顶部角落 = 死区

单手够不到，必须换握姿势。故意把设置、删除卡、放弃这类破坏性操作放这里 —— 麻烦本身就是防误触功能。

!
中段 = 拉伸区

遗物栏、药水槽放这里。玩家需要点，但不该每回合都点，所以放高一点是合理取舍。

✓
底部 1/3 = 舒适区

手牌 + 行动力 + 结束回合，全在这里，占屏高 47%。每回合要点的东西一个都不放在别处。虚线圆弧 = 拇指自然扫过的范围。

✓
敌人意图不放到底部

手指会遮挡自己按住的元素。意图是每回合必读信息，必须在手指够不到的地方（敌身上方）。

触控硬指标

间距比尺寸更影响误触率 —— 这是调研里最反直觉的一条。

目标尺寸标准

Apple HIG
44×44 pt
Material Design
48×48 dp
WCAG AAA
44×44 px
WCAG AA
24×24 px

AA 的 24px 是法律底线，不是设计目标。跨平台安全值是 44px。

间距 = 误触率

实测案例：两个按钮都 44pt 高、相距 4pt，误触率 11%；改成相距 12pt，误触率降到 2%。按钮没变大，只是拉开距离。

相距 4pt
11% 误触
相距 12pt
2% 误触

规则：相邻目标 ≥8pt（目标≥44pt 时）；靠屏幕边缘 80pt 内 → ≥16pt。

StS 踩过的坑 → 对应方案

移动端问题StS 的表现本方案对策
想读卡却打出去了长按放大，但手指稍高就误出牌长按 400ms 放大，牌移到中上部，拇指区清空后再松手出牌
拖动时误放到敌人身上目标吸附但反馈弱拖过阈值（移动 60px 或 200ms）才算拖拽，否则视为点击

技术实现要点

Phaser 3 竖屏配置

const config = {
  type: Phaser.AUTO,
  parent: 'game-container',
  width: 1080,          // 设计分辨率
  height: 1920,
  scale: {
    mode: Phaser.Scale.FIT,
    autoCenter: Phaser.Scale.CENTER_BOTH
  }
};

Scale Manager 是唯一正确的缩放方式。手动改 CSS 或 transform:scale() 会破坏坐标系、输入处理和物理计算。

移动端必需的 CSS

/* 1. 禁止浏览器抢手势 */
canvas { touch-action: none; }

/* 2. 全屏 + 禁滚动 */
html, body {
  overflow: hidden;
  overscroll-behavior: none;
  -webkit-tap-highlight-color: transparent;
  user-select: none;
}

没有 touch-action:none，拖动卡牌会滚动整个页面 —— 这是最常见的移动端 Phaser bug。

viewport meta 不能少：width=device-width, initial-scale=1.0, maximum-scale=1.0, user-scalable=no, viewport-fit=cover 。少了它，移动浏览器会用模拟桌面宽度渲染再缩小，游戏会小到看不清。viewport-fit=cover 配合 env(safe-area-inset-*) 处理刘海和 Home 条。

扇形手牌数学

const root = { x: centerX, y: 1920 + 200 }; // 圆心放屏幕下方外
const size = 1200;      // 扇形半径
const maxAngle = 1.2;   // 总展开角(弧度)

const interval = maxAngle / n;
hand.forEach((card, i) => {
  const rot = (i - (n - 1) / 2) * interval;
  const x = root.x + Math.cos(rot - Math.PI / 2) * size;
  const y = root.y + Math.sin(rot - Math.PI / 2) * size;
});

移动端参数：旋转角 15°（PC 25°）；牌间距 ≥ 牌宽 1/3，否则重叠区会误触；牌数 > 8 时增大半径、减小间距，否则边缘牌出屏。经验公式 size = baseSize + (cardCount - 5) * 2.5。

方案优点缺点建议
Phaser 3 Web已熟悉；迭代快；跨平台；免费性能不如原生；包体小原型验证用这个
Unity + UiCard 上架有开源卡牌 UI 框架；性能好；一键打包 APK学习成本高；授权要上架用这个
Cocos Creator国内生态好；2D 性能强需重新学备选

建议路线：Phaser 3 做原型验证玩法 → 玩法定型后决定是否迁 Unity。如果目标只是「能玩的网页版竖屏卡牌」，Phaser 就够；目标是上架应用商店，Unity 是正解（UiCard 现成框架 + 性能 + 打包）。

竖屏 vs 横屏的核心取舍

这一栏是整个设计的分水岭 —— 每一行都是因为竖屏而必须做的改动。

维度杀戮尖塔（横屏）本方案（竖屏）
敌人数量1~3 个，横排强制 1V1 — 省下的横向空间全给卡牌
卡牌手数55（保持一致，不增加认知负担）
战斗场景敌人横排 + 底部手牌单敌人居中 + 大立绘（视觉冲击换空间效率）
地图15 层连线图竖向节点链，滑动查看
牌组界面网格纵向列表 + 左滑删牌
商店横向布局纵向卡片流 + 底部结算栏
资源能量 3行动力 3（保持，降低学习成本）

新手减负系统（抄月圆之夜）

这是月圆之夜 6 年留存的核心，不是锦上添花。设计时就要埋进去。

降低构筑门槛

  • Key 牌权重高 — 1 张核心卡就能撑起一个流派
  • 流派种子 — 开局 3 选 1 定方向（暴击/护甲/过牌/中毒）
  • 掉落检定 — 卡牌奖励/商店按已有流派偏置掉落
  • 利好事件多 — 首次免费 → 前几次低价 → 后期涨价

降低损失厌恶

  • 进度保存 — 打不过可退回重开，起手重洗
  • 事件保留 — 跳过的事件下次还会遇到
  • 开局伪随机 — 前几局事件池固定（承担教学）
  • 难度分层 — 概率保护随周目数增加而减弱

开发路线

  1. Phase 0 · 1~2 天

    玩法验证

    竖屏 CombatScene + 1 敌人 1 BOSS + 20 张牌。抽牌/行动力/格挡/意图/结算全套。只做点击出牌，不做拖拽。
    验收：浏览器里能完整打完一场战斗。

  2. Phase 1 · 3~5 天

    交互打磨

    手牌自适应布局、长按预览、拖拽 + 目标吸附、防误触、viewport / touch-action 修复、90fps 验证。
    验收：真机连续打 20 场不出现误触翻车。

  3. Phase 2 · 1~2 周

    内容扩充

    地图 + 章节 + BOSS、卡牌奖励/篝火/商店、遗物药水、3~4 个流派方向。
    验收：一局 20~30 分钟通关，能打出至少 3 种流派。

  4. Phase 3 · 视投入

    美术与音

    卡牌插画、敌人立绘、BGM、出牌/受击音效、出牌飞行动画、伤害数字。
    这决定「能玩」vs「想玩」的分水岭，但优先级排在最后。

AI 能力边界（诚实评估）

AI 能做好
  • 卡牌系统 / 效果引擎（数据驱动，扩展容易）
  • 战斗状态机（确定性逻辑正是 AI 强项）
  • 竖屏布局计算（扇形数学、尺寸计算，规则明确）
  • 移动端适配样板代码（有标准答案的工程问题）
AI 做不好
  • 数值平衡 — 60 张牌需几百小时试玩调整
  • 交互手感 — 300ms 还是 400ms，只能真机试
  • 美术 — 画不出 700 张统一调性的插画
  • 流派设计 — 好玩的核心机制只能拼凑已有的
目标可行性
做出能玩的原型证明玩法成立高 可行
做出能上架的完整游戏中 玩法能成，美术和平衡需大量人工投入
做出能和月圆之夜竞争的产品低 需要团队 + 几年
