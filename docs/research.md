# 竖屏卡牌手游 竞品调研 + 设计方案

> 调研时间:2026-10-04
> 目标:做一款**竖屏(9:16)**的肉鸽卡牌构筑手游,对标《杀戮尖塔》系统深度 + 《月圆之夜》竖屏体验

---

## 0. 先说结论(如果你只读一段)

**能做,但不能靠"把横屏 UI 压扁"来做。**

三个调研出来的事实决定了这个项目的方向:

1. **《月圆之夜》之所以能在手机上活下来,不是因为它是《杀戮尖塔》的移植,是因为它改了核心规则。** 它把 StS 的「能量 + 多敌人」改成了「行动力 + 1V1」。这一改,屏幕宽度需求直接砍掉一半,卡牌文字才塞得下。

2. **《杀戮尖塔》移动版在手机上是被差评的。** 多个评测的共识是"手机上 UI 小得像蚂蚁""误触出牌毁了 40 分钟的局""建议买平板"。它的战斗界面是横向信息密度设计(多敌人横排 + 底部手牌),竖屏手机上会崩。

3. **拇指区是硬约束。** Steven Hoober 的研究:49% 用户单手握持。底部 1/3 是唯一舒适区,顶部角落是死区。**竖屏的优势恰好是"底部空间天然充裕"** — 这是月圆之夜选竖屏的根本原因,不是随便选的。

所以我的建议是:**别做 StS 的竖屏版,做"StS 深度 + 竖屏原生设计"的版本。**

## 1. 《月圆之夜》拆解 — 为什么它能成

### 1.1 基础参数

| 项 | 数据 |
|---|---|
| 开发 | 巨人网络 · 滴答工作室 |
| 上线 | 2017.10(PC),移动端 2018 |
| 定位 | 肉鸽 × DBG,单机,买断制无内购 |
| 题材 | 暗黑童话 · 小红帽 |
| 职业 | 10 个(每职业独立卡池 + 核心机制) |
| 卡牌 | 600~700 张 |
| 怪物 | 140+ 种,BOSS 30+ |
| 单局时长 | 15~40 分钟 |
| 美术 | 手绘暗黑童话,统一调性 |
| 商业 | 买断 + 20 个 DLC(总 252 元),后期加了 PvP |

### 1.2 核心规则差异(关键!)

| | 杀戮尖塔 | 月圆之夜 |
|---|---|---|
| 资源 | 能量 3 点 | 行动力(每回合恢复) |
| 对手 | 1~3 个敌人 | **永远 1V1** |
| 胜利条件 | 清空所有敌人血条 | **敌人血条归零** |
| 地图 | 15 层 × 分支连线 | 章节内节点推进,无连线约束 |
| 死亡 | 整局结束 | 整局结束(可回退重试) |

**1V1 是竖屏的关键。** 敌人不需要横排,一张立绘 + 血条 + 意图就够。屏幕横向空间省下来给卡牌。

### 1.3 竖屏设计要点(从资料里能确认的)

- **单手拇指操作**:所有战斗/探索动作拇指可完成,不依赖拖拽
- **牌组界面精简**:卡牌文字清晰、体积适中,兼顾阅读效率和美观
- **支持卡组快速预览**、**滑动排序手牌**
- **战斗界面支持跳过动画** — 手机上单局短,动画要能跳
- **千元机流畅运行** — 意味着美术不能太重
- **触摸/拖拽出牌为主,反馈灵敏**

### 1.4 它的"减负设计"(值得抄的)

官方复盘文档里明确列出的上手减负机制:

| 手段 | 做法 |
|---|---|
| **Key 牌权重高** | 1 张核心卡就能撑起一整个流派,降低构筑门槛 |
| **大量利好事件** | 事件遵循"首次免费 → 前几次低价 → 后期涨价",玩家能低成本试错 |
| **开局伪随机** | 前几次体验的新手,遇到的随机事件类型固定(承担教学功能) |
| **卡牌掉落检定** | 升级奖励/商店/宝箱会检测玩家现有牌组,已有流派影响掉落 |
| **进度保存** | 打不过可以退回重开,起手牌随机刷新 → 失败也有信息成长 |
| **事件保留** | 遇到牌组优化事件但没想好方向,可以选择先去打怪,事件保留到下次 |
| **难度分层** | 模式内爬塔 + 职业间难度进阶,概率保护随周目数增加而减弱 |

**这七条是"新手留存"的核心,不是锦上添花。**

### 1.5 商业化路径(6 年演化)

```
2017.10–2019.01  拓宽经典模式(加职业/卡池)  ← 玩家接受度高
      ↓ 瓶颈
2019.07–2023.01  新玩法模式(自走棋/随从)      ← 突破设计上限
      ↓ 停滞 2 年
2023.08–至今     联机 PvP + IP 联动          ← 靠社交拉时长
```

关键洞察:**核心乐趣(肉鸽×DBG)6 年没变,变的是外壳。** 所有新模式的属性/卡牌类型都继承自经典模式,玩家认知可迁移。

用户量:上线 3 个月拿 App Store 年度最佳本土独立游戏 → 2 年后 Steam → 同年 8 月破 1000 万 → 2021.01 破 2000 万。

## 2. 《杀戮尖塔》移动版拆解 — 它的坑

### 2.1 手机上的批评(多评测共识)

- ❌ **UI 字体小到像蚂蚁**:"读一小时就开始眼疲劳"
- ❌ **误触出牌**:想读卡 = 长按,但手指稍高就打出去了,没有 undo
- ❌ **手势冲突**:上滑出牌 = iOS 切换 App 的手势,"我一半的格挡操作把我送进了邮件"
- ❌ **取消选中手势反人类**:"需要某种随月相变化的手势"
- ❌ **图标太小**:遗物/药水/状态图标要点好几次才搞清楚
- ✅ 平板上体验好很多

### 2.2 它做对的部分(值得抄)

- **长按放大**看卡牌文字 + 关键词解释 → 不在战场上堆常驻 tooltip
- **目标吸附**:拖到敌人上方有明显吸附反馈,减少误放
- **地图可缩放拖动**,节点选择"deliberate and forgiving"
- **可靠自动存档**,中途离开不丢进度
- **UI 动态缩放**适配不同屏幕

### 2.3 它的核心结构问题

**信息密度是横向设计的。** 敌人横排 + 状态图标群 + 遗物栏 + 药水栏 + 底部手牌,这套布局在 16:9 上刚好,压到 9:16 就会:
- 敌人被迫竖排 → 占掉大量纵向空间 → 手牌被挤扁
- 卡牌宽高比固定(约 0.7),竖屏宽度 1080px 下,一张卡最多 ~200px 宽,5 张手牌就重叠严重
- 文字被迫缩到 8px 以下 → 就是"蚂蚁 UI"

**所以:直接移植 = 蚂蚁 UI + 误触地狱。**

## 3. 竖屏卡牌 UI/UX 规范(硬指标)

### 3.1 拇指区(Steven Hoober 研究)

```
┌─────────────────────┐
│  ❌ 死区(难区)       │  顶部角落,需要换手 → 手机最容易掉
│   ← 单手够不到        │
│                     │
│  ⚠️ 拉伸区           │  中部,需要伸
│                     │
│  ✅ 舒适区           │  底部 1/3,拇指自然弧线
│    ← 核心操作放这     │
└─────────────────────┘
```

- 单手持机 49%,双手托持 33%,双手 18%
- **60%+ 的触摸交互发生在屏幕下半部**
- 关键操作绝不能放在屏幕高度 70% 以上
- **破坏性操作(删除卡、放弃)故意放顶部难区** — 麻烦本身就是功能

### 3.2 触控目标尺寸

| 来源 | 最小值 |
|---|---|
| Apple HIG | 44 × 44 pt |
| Google Material | 48 × 48 dp |
| WCAG 2.5.5 (AAA) | 44 × 44 CSS px |
| WCAG 2.5.8 (AA) | 24 × 24 CSS px(有间距时) |

**间距比尺寸更重要。** 实测案例:两个按钮都 44pt 高、相距 4pt,误触率 11%;改成相距 12pt,误触率降到 2%。

间距规则:
```
相邻目标间距 ≥ 8pt(当目标 ≥ 44pt)
靠近屏幕边缘 80pt 内 → 间距 ≥ 16pt(手指斜着伸进来更不准)
```

**手指遮挡问题**:手指按下时会盖住目标。所以视觉反馈要"从手指下扩散出去"(Material ripple 那种),不能只在手指下面变个色。

### 3.3 安全区

```css
padding-top: env(safe-area-inset-top);      /* 刘海 */
padding-bottom: env(safe-area-inset-bottom); /* Home 指示条 */
```
- 主交互元素距屏幕边缘留 8~16px,避免和系统返回手势打架
- iPhone 底部 Home 条约 34px,必须避开

### 3.4 文字与图标

- 移动端游戏 UI 文字**不得低于 12pt**(原生分辨率)
- 图标可见尺寸可以小(16~24px),但**触控热区必须 44×44 以上**
- 竖屏卡牌正文建议 **14~16px** 起(设计分辨率下),比 StS 手机版大一倍

## 4. 技术实现方案

### 4.1 引擎选型

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **Phaser 3 (Web)** | 你已熟悉;迭代快;跨平台;免费 | 性能不如原生;包体小 | ✅ **v0 原型用这个** |
| **Unity + UiCard** | 有现成卡牌 UI 框架(开源);性能好;能直接出 APK | 学习成本高;Unity 授权 | ✅ **要上架用这个** |
| **Cocos Creator** | 国内生态好;2D 性能强;包体小 | 需重新学 | 🟡 备选 |
| **Flutter + Flame** | UI 层强;动画顺滑 | 游戏性能一般;生态弱 | ❌ 不推荐 |

**我的建议:Phaser 3 做原型验证玩法 → 玩法定型后决定是否迁 Unity。**
如果目标只是"做出一个能玩的网页版竖屏卡牌",Phaser 就够。如果是"上架应用商店",Unity 是正解(有 UiCard 现成框架 + 性能 + 一键打包)。

### 4.2 Phaser 3 竖屏配置(可直接用)

```js
const GAME_W = 1080;   // 设计分辨率宽
const GAME_H = 1920;   // 设计分辨率高 (9:16)

const config = {
  type: Phaser.AUTO,
  parent: 'game-container',
  width: GAME_W,
  height: GAME_H,
  scale: {
    mode: Phaser.Scale.FIT,               // 等比缩放到屏幕
    autoCenter: Phaser.Scale.CENTER_BOTH, // 居中
    parent: 'game-container'
  },
  scene: [ BootScene, CombatScene, ... ]
};
```

**关键点(来自 Phaser 官方文档):**

1. **Scale Manager 是唯一正确的缩放方式。** 手动改 CSS 或 `transform: scale()` 会破坏 Phaser 的坐标系、输入处理、物理计算 —— 是反模式。

2. **父容器必须有明确尺寸**,否则 autoCenter 会失效:
   ```css
   #game-container {
     width: 100vw;
     height: 100vh;
     overflow: hidden;
     background: #000;   /* letterbox 区域填黑 */
   }
   ```

3. **父容器不要加 padding**(Scale Manager 不计算),要留白就加 margin 或加在父元素的父元素上。

### 4.3 移动端必需的 HTML/CSS

```html
<!-- 1. viewport meta,禁止用户缩放 -->
<meta name="viewport"
      content="width=device-width, initial-scale=1.0,
               maximum-scale=1.0, user-scalable=no,
               viewport-fit=cover">
```

```css
/* 2. 禁止浏览器抢手势,否则拖动卡牌会变成滚动页面 */
canvas { touch-action: none; }

/* 3. 全屏铺满,禁止页面滚动和回弹 */
html, body {
  margin: 0; padding: 0;
  width: 100%; height: 100%;
  overflow: hidden;
  overscroll-behavior: none;   /* 禁止下拉刷新 */
  background: #000;
  -webkit-tap-highlight-color: transparent;  /* 去掉点击蓝色高亮 */
  -webkit-touch-callout: none;              /* 去掉长按菜单 */
  user-select: none;
}
```

**没有 `touch-action: none`,拖动卡牌会滚动整个页面** —— 这是最常见的移动端 Phaser bug。

### 4.4 DPR 处理

Phaser 的 Scale Manager 内部处理 DPR。关键配置:

```js
scale: {
  mode: Phaser.Scale.FIT,
  // 不要设 resolution,用 Phaser 的自动 DPR 处理
}
```

如果用 `RESIZE` 模式(推荐给 UI 密集型游戏):
```js
scale: { mode: Phaser.Scale.RESIZE }
// 然后在场景里用 this.scale.gameSize 拿当前尺寸
// 监听 this.scale.on('resize', (gameSize) => {...})
```

⚠️ RESIZE 模式的坑:canvas 尺寸 = 父容器尺寸,如果父容器很大,GPU 填充率压力会上升。移动端要配合裁剪。

### 4.5 触控事件

Phaser 的 pointer 事件统一了鼠标/触摸/笔,用一套 API:

```js
// 按下 / 抬起 / 移动 / 取消
this.input.on('pointerdown', (pointer) => {...});
this.input.on('pointerup',   (pointer) => {...});
this.input.on('pointermove', (pointer) => {...});
this.input.on('pointerout',  (pointer) => {...});

// 多点触控(双指缩放等)
this.input.addPointer(2);
```

⚠️ **必须处理 `pointercancel`** — iOS 在来电、来通知、锁屏时会发 cancel,不处理会导致卡牌卡在"拖拽中"状态。

### 4.6 扇形手牌数学(StS 风格)

StS 的手牌是**扇形排布**,不是平铺。数学很简单:

```js
// 极坐标 → 笛卡尔
const root = { x: 手牌中心X, y: 画布底部 + 200 };  // 圆心放在屏幕下方外
const size = 1200;  // 扇形半径
const maxAngle = 1.2;  // 弧度,总展开角

const n = hand.length;
const interval = maxAngle / Math.max(n, 1);   // 每张牌的角度间隔

hand.forEach((card, i) => {
  // 居中分布
  const rot = (i - (n - 1) / 2) * interval;
  const x = root.x + Math.cos(rot - Math.PI / 2) * size;
  const y = root.y + Math.sin(rot - Math.PI / 2) * size;
  const rotation = rot * 180 / Math.PI;  // 角度转弧度给 Phaser
});
```

**移动端参数建议(基于 Unity 实战文章):**
- 移动端:旋转角 15°(PC 端 25°)
- 移动端:间距压缩,牌间距 ≥ 牌宽的 1/3,否则重叠区会误触
- 牌数 > 8 时:增大半径,减小间距,否则边缘牌超出屏幕
- 经验公式:`size = baseSize + (cardCount - 5) * 2.5`

**移动端关键改动:平铺比扇形好。**
扇形在触屏上"牌与牌重叠区域难判断点到了哪张"。建议:
- ≤ 4 张手牌:扇形(好看,单手好点)
- ≥ 5 张手牌:**平铺 + 选中时上移放大**(判断更准)

### 5.2 拇指区分配(对照上文规范)

| 元素 | 位置 | 高度占比 | 符合规范? |
|---|---|---|---|
| 敌人立绘 + 意图 | 上部 | 27% | ✅ 只看不点 |
| 玩家状态 | 中部 | 11% | ✅ 只看 |
| **手牌** | **下部** | **36%** | ✅ 舒适区核心 |
| **行动力 + 结束回合** | **最底** | **11%** | ✅ 舒适区 |
| 遗物 / 药水 | 顶部 | 9% | ⚠️ 难区(但只看不点) |
| 设置 / 菜单 | 顶部角落 | — | ✅ 故意放难区 |

**每回合要点的按钮,全部在底部 1/3。**

### 5.3 卡牌尺寸计算

1080 宽设计分辨率下:

| 手牌数 | 牌宽 | 间距 | 总宽 | 说明 |
|---|---|---|---|---|
| 3 | 260 | 20 | 820 | 大牌,视觉冲击强 |
| 4 | 230 | 16 | 952 | 舒适 |
| 5 | 190 | 14 | 1018 | **最常见** |
| 6 | 165 | 10 | 1030 | 略挤 |
| 7 | 140 | 8 | 1024 | 重叠开始明显 |
| 8 | 120 | 6 | 996 | 需要选中才看得清 |

牌比例:**2:3 或 5:7**(接近实体扑克牌)。190px 宽 → 285px 高。

**牌数 > 5 时启用"选中上移 + 其余下沉"策略**,不要单纯缩小牌宽(缩到 140px 以下文字就不可读了)。

### 5.4 移动端防误触方案(抄 StS 的教训)

| 问题 | 方案 |
|---|---|
| 想读卡却打出去了 | **长按 400ms 放大预览,抬手前不出牌**。放大预览出现后,牌移到屏幕中上部,拇指区域清空 |
| 拖动时误放 | **拖过阈值(牌移动 60px 或时间 200ms)才算拖拽**,否则视为点击 |
| 目标选错 | **目标放大 1.15x + 描边高亮 + 震动反馈**,手指下方也要有可见反馈 |
| 选中卡后想取消 | **拖回手牌区松手 = 取消**(不是"猜手势") |
| 牌重叠难判断 | **选中的牌 zIndex 提到最顶 + 上移 40px** |
| 手指遮挡文字 | 战斗中的关键信息(敌人意图)**不放到底部**,放敌人身上 |

### 5.5 竖屏 vs 横屏的取舍(和 StS 的根本差异)

| | StS(横) | 本方案(竖) |
|---|---|---|
| 敌人数量 | 1~3 | **强制 1V1** |
| 卡牌手数 | 5 | 5 |
| 行动力 | 能量 3 | 行动力 3(保持) |
| 战斗场景 | 敌人横排 | **单敌人居中 + 大立绘** |
| 地图 | 15 层连线图 | **竖向节点链,滑动查看** |
| 牌组界面 | 网格 | **纵向列表 + 左滑删牌** |
| 商店 | 横向布局 | **纵向卡片流 + 底部结算栏** |

## 6. 系统设计建议(基于月圆之夜的教训)

### 6.1 必须做的"减负"系统

| 系统 | 做法 | 目的 |
|---|---|---|
| **流派种子** | 开局给玩家 3 选 1 的"核心方向"(暴击/护甲/过牌/中毒) | 降低构筑门槛,新手不会乱抓 |
| **掉落检定** | 卡牌奖励/商店根据玩家已有流派偏置掉落 | 加速成型,减少废卡 |
| **事件保留** | 玩家选择"跳过"的事件保留,下次再遇到 | 消除"必须做决定"的压力 |
| **进度保存** | 打不过可以退回重开,起手重洗 | 失败 = 信息成长 |
| **难度分层** | 前期事件池固定(教学),后期全开 | 概率保护 |

### 6.2 卡牌系统

**规模建议(v0 目标):**
- 卡牌:60~80 张(不是 700 张)
- 敌人:20~25 种 + 3 个 BOSS
- 遗物/祝福:20~30 个
- 职业/流派:3~4 个核心方向

**数据结构(可参考现有 `slay-the-spire-clone`):**
```js
{
  id, name, type, rarity, cost, target, desc,
  effects: [{ kind: 'damage', value: 6 }],
  upgraded: { desc, effects },   // 升级版
  exhaust: false                 // 是否消耗
}
```

这个 schema 已经在上一个项目验证过可行(25 张牌跑通完整战斗循环),可直接复用扩展。

### 6.3 主题选择建议

如果不做童话,**国风志怪**(《牌师》路线)或**克苏鲁**(《古神遗踪》路线)在国内容市场更有差异化,而且:
- 避开和月圆之夜(童话)正面竞争
- 手绘水墨/暗黑插画风格在小体量下更容易做出统一调性
- 敌人设计空间大(妖怪谱系),不容易审美疲劳

## 7. 开发路线建议

### 阶段 0:玩法验证(1~2 天)
**目标:确认核心循环好玩,而不是好看。**

- 竖屏布局 CombatScene(Phaser 3)
- 1 个敌人 + 1 个 BOSS
- 20 张牌
- 抽牌/能量/格挡/意图/结算
- 只做点击出牌,不做拖拽

**验收:能在浏览器里完整打完一场战斗。**

### 阶段 1:交互打磨(3~5 天)
**目标:解决移动端手感问题。**

- 扇形/平铺手牌(自适应)
- 长按预览
- 拖拽出牌 + 目标吸附
- 防误触
- 移动端 viewport + touch-action 修复
- 90fps 验证

**验收:在真机上连续打 20 场不出现误触导致的翻车。**

### 阶段 2:内容扩充(1~2 周)
- 地图 + 章节 + BOSS
- 卡牌奖励 / 篝火 / 商店
- 遗物 / 药水
- 3~4 个流派方向

**验收:一局 20~30 分钟能通关,能打出至少 3 种流派。**

### 阶段 3:美术与音(视投入)
- 卡牌插画 / 敌人立绘
- 基础音效(BGM + 出牌/受击/胜利)
- 动画(出牌飞行、受击闪白、伤害数字)

**这是决定"能玩"vs"想玩"的分水岭,但优先级在最后。**

## 8. AI 能力边界(诚实评估)

延续之前的判断,这次调研后更清楚:

### AI 能做好
- ✅ **卡牌系统 / 效果引擎** — 数据驱动,扩展容易
- ✅ **战斗状态机** — 这类确定性逻辑正是 AI 的强项
- ✅ **竖屏布局计算** — 扇形数学、尺寸计算,给规则 AI 能写对
- ✅ **移动端适配的样板代码** — viewport / touch-action / Scale Manager,这些是有标准答案的

### AI 做不好
- ❌ **数值平衡** — 60 张牌的数值需要几百小时试玩调整,AI 只能给"看着差不多"的值
- ❌ **交互手感** — "扇形好还是平铺好""长按 300ms 还是 400ms""牌移动 40px 还是 60px",这些只能靠真机试
- ❌ **美术** — 商业级卡牌插画 AI 画不出 700 张统一调性的
- ❌ **流派设计** — 好玩的核心机制设计,AI 只能拼凑已有的

### 所以项目的现实定位

| 目标 | 可行性 |
|---|---|
| 做出**能玩的原型**证明玩法成立 | ✅ 高 |
| 做出**能上架的完整游戏** | ⚠️ 玩法能成,美术和平衡要大量人工投入 |
| 做出**能和月圆之夜竞争的产品** | ❌ 需要团队 + 几年 |
