## 2. 优化方向与优先顺序

### R1：让玩家拿到包就能玩，进度可靠保留

**目的：建立独立于开发环境的 Windows 试玩载体。**

- 保留 Phaser 与网页版本，增加桌面容器；优先验证 Electron 等成熟方案，不重写引擎。用当前受支持版本和锁文件，先验证本地资源、音频、字体、弹窗和打包兼容性。
- 交付可解压运行包与安装包，玩家不安装 Node/Python、不启动服务器、不依赖 GitHub Pages。包内资源完整，断网可玩。
- 打通用户数据目录中的文件存档：本局、备份、收藏、语言、音效、音乐、减少动态和阅读字号。以实际扫描得到的全部键为准，不能只迁移 `darkforest.run`。
- 在原有检查点语义下处理关闭、强退、更新、损坏与失败提示；不承诺保存未支持的战斗中途状态。
- 提供玩家主动导出网页数据、导入桌面版的途径；不读取其他浏览器的私有目录。区分正式与测试资料目录，避免测试污染玩家进度。
- 完成窗口/全屏、Alt-Tab、退出、恢复焦点等基础操作；整体横屏重排留给 R2。

**交付：**构建命令、锁文件、两个候选包、文件清单与哈希、存储契约、实测记录、剩余缺陷。详细验收见下一步提示词。R1 不改卡牌数值、敌人招式、奖励经济或默认实验开关。

### R2：让第一次进入游戏的人看得懂、操作得准

**目的：解决桌面阅读与前十五分钟的理解成本。**

- 先在 1280×720/1366×768、1920×1080、2560×1440 和 100%/125%/150% 系统缩放下记录问题。截图必须记录实际窗口客户区、缩放与语言，不能只测逻辑坐标。
- 保留中央战斗构图；宽屏余量用于选中卡完整说明、敌人意图与状态详情。窄窗口回到现有可读布局，不把竖屏整体拉宽。
- 将查看、出牌、取消、费用不足四种状态分清；鼠标、数字键、Esc 和阅读面板不得互相抢输入。开菜单时暂停战斗输入，关闭后焦点可恢复。
- 开场教学按遭遇逐步展示：第一战观察意图与格挡，第二战展示该传承的一次组合，首次奖励解释拿牌/跳过与精简。可以跳过、重看，不用长篇弹窗一次灌完所有规则。
- 音效和特效用于解释结算：盾吸收、破盾、扣血、持续伤害、回复必须能区分；敌人绝招提示先于结算。已有功能先检验清晰度，再针对缺口补素材。

**交付：**中英关键场景截图、正常/九牌/长文本/费用不足/多状态的输入与布局证据，一段无指导首局录像；先邀请 8–12 名非开发者找问题。内部目标为至少 80% 能独立完成首战并理解基本资源，但小样本只用于发现问题，不能证明市场成功。未通过则留在 R2 修正。

### R3：让三套传承有不同决策，让敌人有可理解的反制

**目的：验证策略性，解决单一最优选择。分批推进，不一次打开全部实验。**

1. **基线校验：**固定当前默认规则和测试版本，复核场景与模拟器的资源、奖励、状态结算一致。记录三套传承的逐战失血、回合数、构筑变化和失败原因。
2. **符咒平衡实验：**保留“灵韵跨回合准备、共鸣连打”的身份作为首轮假设。分别评估基础牌效率、共鸣收益、资源供给的单变量候选；一次只改一个候选族，不同时削卡、改回复、增强敌人。若始终存在支配策略，再单独评估资源累积规则。这里不凭旧 A/B 数字直接指定最终数值。
3. **特色初始牌实验：**分别测试已有六张原型。猎血关注即时追猎与留流血的取舍；守御关注完整防守后的反攻与当回合输出；符咒关注铺印与引爆时机。每次只替换一套开局；敌人与经济固定。卡牌 ID、存档实际牌组与文本预览必须一致。
4. **敌人实验：**先测试灰狼/头狼的预告—扑击—恢复，之后每批最多两名敌人。每个招式写清触发、伤害/状态、结算时点、玩家反制、强度预算和提示方式。优先复用流血、毒、虚弱等已有状态；暂不新增可连续剥夺玩家整回合的眩晕链。

**观察要求：**离线 A/B 用来筛数值与规则，真人用来回答出牌顺序、理解和乐趣。单次试玩至少观察到第十战；验收样本必须覆盖升契之后、后九战与 BOSS，不能以前三战代替。调试快胜只能验流程。

**实验方法：**先做每臂 300 个配对种子的探索筛查，锁定候选后再用新的种子批次确认；必要时扩样本。记录样本数、种子范围、版本、实验开关、胜率差与不确定性、配对翻转、逐战曲线和截断次数。相同种子并不保证变更出牌后所有抽牌序列相同，需验证独立随机域与实验配对前提。不要反复用同一批种子挑选并宣称确认。

**通过条件：**各传承有可以复现的成功策略及可解释代价，真人能举出由敌人意图改变出牌顺序的例子；不存在明显资源无限循环或广泛支配的玩法。三套胜率不必完全相同。反复出现超过 10 个百分点的差距列为调查信号，不是硬性平衡线。妖契延迟价值先用定向遭遇和真人操作观察，暂不投入完整前瞻 AI。

### R4：证明值得再玩，再补最缺的内容

**目的：检验重复游玩的价值，确定正式版范围。**

- 组织不少于 20 名目标玩家的多次试玩，记录是否有时间继续、是否主动重开，以及原因；不把招募者的“觉得不错”当付费意愿。
- 第一轮固定三套传承轮换观察，后续允许自由选择；记录主动选择与被分配体验的差别。观察完整一局及至少一次重开，保留没玩完的退出原因。
- 目标是每套传承至少有两种成立的构筑方向。先利用现有卡、妖契、遗物与商店；若第二局仍重复，再选一个增量做对照。
- 根据证据选择下一批：路线变化、妖契分支、敌人组合，或真正的卡牌改造。若选真改造，单独迁移卡牌实例与旧档、洗牌、奖励、删牌和 UI；不能再用随机换牌声称完成升级系统。
- 对东方篇、BOSS、剧情、结局做连续听感验收，再决定音乐增补；英文由能理解卡牌规则的使用者审校，修完后才去掉“预览”。

**通过条件：**有重复开局行为和具体动机的证据，内容时长与价格预期有依据，能说明相对其他卡牌游戏的独特决策。若缺乏重玩动机，回到 R3/R4 修改，不用数量补齐的方式掩盖。暂不扩大到更多语言、职业或联机。

### R5：冻结版本，完成发行准备

- 最低配置来自实际机器测量；候选版覆盖三档电脑、至少 50 次完整流程测试。记录真人/自动、正常战斗/快胜、版本与设备；不能把不同版本结果凑成一次验收。已知崩溃、卡死、丢档与阻断进度的问题清零。
- 建立可复现构建、测试分支、旧档升级与回退策略、日志和反馈入口。回退不能偷偷覆盖较新格式存档。
- 梳理素材、字体、引擎、音频、文本与生成服务来源和使用条件；记录 AI 实际参与方式。程序合成音频与生成模型音频要准确区分，不能由工具名称推断是否需要披露。
- 制作实机截图、玩法预告、胶囊/库素材、商店描述、支持语言、配置、支持联系方式与价格。商店承诺只包含已实现并验证的内容。
- Steam 成就、云存档、手柄/Steam Deck 按目标受众排期；本地成就不等于 Steam 成就，云同步还需冲突测试。未实现则不勾选支持。

**通过条件：**工程与体验门槛通过，商店页与构建审核通过，账号及等待期满足，再决定发布。不以完成 R1 或逻辑测试全绿宣布已可售。

## 3. 每次交付统一报告

每个阶段提交：目标与范围、基线版本、实际修改、验收方法、原始输出/截图/录像、失败与未测项目、回退办法、下一阶段建议。明确标注“通过 / 失败 / 未测 / 外部依赖”，环境不可用的项目不写成通过。

真人记录字段：匿名编号、卡牌经验、版本/开关/设备、传承/难度、帮助次数、关键选择及理由、到达战次、死亡原因理解、主动重开与原因、文本/声音问题。取得同意后记录，默认本地保存，不先增加在线埋点服务。

阶段评审只放行已被证据支持的工作包。无需把后续全部细节一次设计完；每批结果决定下一批具体范围。账号/付款/身份、真人招募、人工语言审校和真正干净设备测试需要相应人员或环境，Agent 可以准备材料，不能制造完成记录。
