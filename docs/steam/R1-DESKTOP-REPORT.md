## 2. 实际方案与理由

### 2.1 容器：Electron 44.9.0

选 Electron 的理由：现有代码是零构建的全局脚本 + Phaser 3.80.1 本地部署，Electron 可以在**不重写引擎**、
不改一行游戏逻辑的前提下提供一个成熟桌面壳（安装/卸载、资源打包、窗口管理、文件存储）。
执行时 Electron 最新稳定版是 44.9.0，electron-builder 是 26.15.3，依赖锁定在 `desktop/package-lock.json`。

没有选其它方案：全程没有出现需要换容器的兼容性或包体证据。

### 2.2 资源加载：受控本地协议 `app://bundle`

原页面不能假定在 `file://` 下可用（`fetch` 与模块加载受 origin 限制），也没有关闭 `webSecurity`。
做法是在主进程注册特权方案 `app://`，由主进程从包内目录读文件并返回：

- 路径先 `path.resolve` 再校验必须落在资源根内，目录穿越直接 403。
- 自带 ETag（mtime + size），重复启动走 304，冷启动不至于每次重读全部素材。
- 断网由两层兜底：页面 CSP 的 `default-src 'self'` 先拦一道，会话层 `webRequest.onBeforeRequest`
  再掐断所有非 `app:` / `data:` / `blob:` 的请求。

### 2.3 隔离

| 项 | 取值 |
|---|---|
| `nodeIntegration` | `false` |
| `contextIsolation` | `true` |
| `sandbox` | `true`（渲染进程与 preload 都在沙箱里） |
| `webSecurity` | `true`（没有关掉） |
| preload 暴露面 | 只有：经过键名校验的存储读写、进度文件导入导出、窗口全屏状态 |
| 新窗口 | 一律 `deny` |
| 外部导航 | 一律拒绝并记日志 |
| 权限请求 | 一律拒绝 |
| CSP | `default-src 'self'`；游戏用了内联脚本，保留 `'unsafe-inline'` |

页面拿不到 `ipcRenderer`、Node、文件系统或命令执行接口。主机端的导入校验用的是
**游戏本体的同一套规则**（`RUN._parseSave` / `META_PROGRESS.validateRaw`），在主进程里用 vm 沙箱求值，
不是另写一份镜像实现。

### 2.4 存储

网页版与桌面版共用 `src/core/storage-backend.js` 定义的接口，键名、值格式、读写语义完全一致；
差别只在落地方式（`localStorage` ↔ 用户数据目录里的文件）。详见 [存储契约](STORAGE-CONTRACT.md)。要点：

- 八个键：本局、上一检查点备份、收藏与成就、语言、音效、音乐、减少动态/触感、阅读字号。
- 桌面端写入用「临时文件 → fsync → 旧主档轮转到 .bak → 原子改名」，主档永远是一份完整数据。
- 损坏主档回落到 .bak；两份都坏时保留原文件并提示；写入失败不影响已有数据。
- 来自更新版本的存档既不覆盖也不删除，玩家在标题页明确确认后才可丢弃。
- 正式资料与测试资料用 `--profile` 分开，测试不污染玩家进度。

### 2.5 构建

```
desktop/
├─ package.json          容器与打包配置（依赖版本写死，锁文件在 package-lock.json）
├─ package-lock.json
├─ main.js               主进程：协议、窗口、IPC、网络拦截
├─ preload.js            受限桥接
├─ lib/                  store / transfer-service / game-validator / window-state / logger
├─ build/
│  ├─ collect-assets.js  算出运行包真正需要的资源
│  ├─ stage.js           整理资源 + 生成 manifest.json（大小 + SHA-256）
│  ├─ make-icon.js       生成应用图标
│  └─ package.js         调 electron-builder 出安装包与运行包
└─ app/                  构建产物（运行资源 + 清单），不入 Git
```

构建时先算出「运行期真正会被请求的资源」再收录：把游戏本体的资源定义放进 vm 沙箱求值，
得到卡面表、事件插画表、动作序列、图标表、音效表，再按 `ASSET_VARIANTS` 映射到实际的 webp，
最后再扫一遍源码里的每一个 `assets/` 片段做自检。**这个自检抓出过两个真实的漏项**：
`assets/hand-reader.css`（带 `?v=` 缓存串，正则没匹配上）和运行时按 id 现取的 BGM
（`assets/audio/bgm-*.ogg|m4a`）。前者会让所有 HTML 弹窗失去样式，后者会让音乐完全不出声——
两个都不会让构建报错，只会让打出来的包少东西。

## 3. 构建与启动命令

```powershell
# 依赖（干净副本上可复现）
cd desktop
npm ci

# 只整理运行资源 + 生成清单
node build/stage.js

# 出两个候选包（安装包 + 可解压运行包）
node build/package.js

# 开发模式直接跑
cd desktop
npx electron .
```

从源码重建到可运行产物的完整链路：`npm ci` → `node build/stage.js` → `node build/package.js`。

运行包解压后直接运行 `Black Forest.exe`；安装包双击安装，按向导选目录（普通用户权限即可，
`perMachine: false`，不写 HKLM）。

| 主档损坏 | 回落到备份，坏文件保留 | 状态 `recovered`，本局仍能读出，坏文件原样保留 |
| 主档损坏且侧车也没了 | 回落到游戏级备份 `darkforest.run.backup` | 状态 `recovered`，本局仍能读出 |
| 主档与备份都坏 | 报损坏，两个文件都保留 | 状态 `corrupt`，主档与备份都还在 |
| 来自更新版本的存档 | 既不覆盖也不删除 | 状态 `future`，文件内容未被改动 |
| 中断写入的残留 `.tmp` | 不影响主档 | 读到的主档有效 |
| 主档只读（拒写） | 写入失败并如实上报，旧数据不坏 | 写入返回 `false`、状态 `writeFailure`、原有数据未被破坏 |
| 资料目录建不出来 | 写入失败而不是静默丢数据 | 写入返回 `false`、状态 `writeFailure`、程序仍正常退出 |

### 跨端迁移（网页导出 → 桌面导入）

| 检查 | 实测 |
|---|---|
| 导入 7 个键 | 全部写入，值与来源文件一致（语言 en、字号 26、音效/音乐/界面设置、收藏 4 张卡） |

## 8. 性能数据

机器：本机 Windows 10.0.26200 x64，Node v22.22.0，Electron 44.9.0 x64。
计时口径：**从进程启动算起**（主进程记录 `PROCESS_START`，探针在条件满足时回报 `afterMs`），
不含开发服务器，也没有任何限速。资源来自包内 `app://`。

| 指标 | 数值 |
|---|---|
| 安装包体积 | 152.47 MB（159 875 260 B） |
| 可解压运行包体积 | 192.24 MB（201 580 495 B） |
| `win-unpacked` 运行目录 | 415.8 MB（436 051 106 B，含 Electron 运行时） |
| 应用资源（`app-web`） | 281 个文件，47.15 MB |
| 五次冷启动 → 标题可用 | 4077 / 3591 / （超时）/ 4085 / 3524 ms（4 次取到数据，min 3.52 s，max 4.09 s，均值 3.82 s） |
| 五次冷启动 → 首战可操作 | 7492 / 6683 / （超时）/ 7352 / 7024 ms（min 6.68 s，max 7.49 s，均值 7.14 s） |
| 桌面进程组内存（战斗场景中） | 5 个进程，工作集合计峰值 1277 MB、私有内存合计峰值 1521 MB；8 秒后均值 1247 MB |

内存口径说明：工作集是**各进程工作集相加**，Electron 的渲染/GPU/网络进程之间共享大量页面，
相加会重复计算共享页，所以这个数是上界而不是实际占用；私有内存合计 1521 MB 是各自的独占部分。
这一项只做记录，不当作性能结论——它受机器内存与显卡驱动影响很大。

冷启动只做了一次机器、一次连续测量的采样，没有跨机器或跨系统缩放比对；
同一台机器上跑两轮的结果在标题 3.0–4.1 s、首战 6.0–7.5 s 之间浮动（系统文件缓存与机器负载有影响）。
**D11 记为「部分通过」**：五次里第 3 次因机器当时负载较高、180 秒内没走完流程而超时，
该次没有取到数据（不算失败，但也不是一次成功的采样），因此实际有效样本是 4 次。
`docs/optimization/` 里网页版那些限速数字是另一套口径，不能和这里直接比较。

## 10. 缺陷与待测项

### 10.1 本阶段发现并已修掉的真问题

| # | 问题 | 后果 | 处置 |
|---|---|---|---|
| 1 | 主进程读接口返回 `{status, value}`，渲染端只认 `{ok, value}` | **桌面版读不回任何进度**，「继续征途」不出现，等于每局都是新开局 | 统一返回形状；补 `tools/test-desktop-integration.js`：用真的 `FileStore` 做端到端联调，不再是内存假后端 |
| 2 | `SAVE_STORE.write` 忽略存储后端返回的 `false` | **磁盘写不进去时界面照样弹「已保存」**，玩家以为进度保住了其实没有 | 改为如实上报 `writeFailure` 并返回 `false`；补回归用例（后端用「返回 false」而不是抛异常来失败） |
| 3 | 构建期资源清单的正则没处理 `?v=` 缓存串 | 运行包漏掉 `assets/hand-reader.css`，**所有 HTML 弹窗失去样式** | 修正正则；加「源码里每个 `assets/` 片段都必须有归属」的自检 |
| 4 | 资源清单没覆盖运行时按 id 现取的 BGM | 运行包**没有音乐文件**，游戏全程无声 | 补规则收录 `assets/audio/bgm-*.ogg/m4a`（不含 .wav 源） |
| 5 | 未来格式保护只挡了游戏内 `schemaVersion`，没挡磁盘信封 `format` | 来自更新版本的存储格式会被静默覆盖 | 存储层也加保护，命中即拒绝写入与删除 |
| 6 | 失败分支下 `SAVE_STORE.clear()` 仍可能删掉主档 | 未来格式的存档可能被清掉 | 清除也走同一套保护，只有玩家明确确认才强制清除 |

### 10.2 未测 / 外部依赖

- **D10 干净 Windows 机器未测。** 本机装了 Node/Python、Z: 盘上有项目源码，不能用开发机替代干净机。
  替代验证只覆盖了「不依赖 Node/Python」这一条。**R1 因此不能宣称已全验收。**
- **未签名。** 见第 9 节。对外分发前必须解决；内部试玩分发不受影响。
- **两版桌面包之间的升级演练未做**（D07 的一部分）：这是第一个桌面包，没有「上一版」可演练。
  旧存档跨端迁移本身已验证（见第 7 节 D07 行）。
- **未覆盖的既有范围**：多点触控、屏幕阅读器全流程、真实音响听感、手柄与 Steam Deck。

### 10.3 已知但不在本阶段修的

- **战斗中途关闭恢复到上一个已落盘检查点**，不是任意时刻续战——这是设计上的边界，不是缺陷（见存储契约第 4 节）。
- **存储接口是同步的**（`ipcRenderer.sendSync`）。好处是现有代码的同步语义原样保留、成功提示严格对应真实落盘；
  代价是主进程在渲染进程线程上做文件 I/O。当前数据量（几十 KB）下无可见影响，
  但如果将来要写入更大的存档（例如战斗快照），需要改成异步并同步改造调用链。
- **Electron 进程组的内存合计偏大**（见第 8 节），需要在 R5 的三档机器上复测。
- **源码注释与调试参数的实际写法不一致**：`src/scenes/TitleScene.js` 写「`?debug&auto=1` 时跳过标题」，
  但代码判的是 `q.get('debug')`——`?debug`（无值）是空串、判假，**必须写 `?debug=1&auto=1`**。
  本轮的验收脚本一开始踩了这个坑（奖励页场景点不开）。
  **已把该处注释改对**（只改注释，不改行为）。

### 10.4 验收工具自身的几处坑（已修，供参考）

- `waitFor` 表达式写成 `(()=>条件)` 而不是 `(()=>条件())` 时，表达式求值成一个函数对象而不是结果，
  条件永远不满足 → 白等到超时。已改成「结果是函数就替它调用一次」。
- 多次冷启动必须用**各自独立的资料目录**：共用时第二次起标题变成「继续征途」，按钮位置变了，
  固定坐标点空，测出来的不是冷启动而是空等。
- **写死坐标点按钮会时灵时不灵。** 商店按钮第一次点开了、第二次没点开——按钮的视觉框与命中区
  未必重合（皮肤按钮就是这种情况）。现在输入器支持 `clickAt`：在点击那一刻从页面问出对象的实际位置，
  再点那个位置，不再靠猜坐标。
- 另有一处未修的小毛病：探针在跑完输入脚本后仍等「标题场景处于活动状态」，
  而流程已经把画面推进到战斗，于是每次白等 180 秒。**只影响验收脚本的耗时，不影响结果**，
  但复用这套工具时值得先改掉。

## 11. 下一阶段建议

R1 到此为止，不自行推进 R2–R5。下面是给设计侧排下一阶段用的建议顺序，
每条都对应本轮留下的具体缺口，不含 R1 范围外的猜测。

1. **先补 R1 的两个空缺，再开 R2。**
   - 一台干净 Windows 机器（或一台装好后拔掉开发环境的虚拟机）跑一遍 D10：解压包 → 启动 → 离线进战斗 → 退出 → 重开。
   - 「两版桌面包之间的升级演练」：等 R2 出第二个桌面包时补；或现在人工造一份「旧格式磁盘信封」来演练。
   这两条不补，R1 的结论只能算「在开发机上成立」。
2. **R2 之前先确认「第一次进来的人看不看得懂」这件事怎么测。**
   本轮把「奖励→商店→继续」用真实输入补齐了（此前只在场景层验证可达），
   但**真人第一次上手的成本完全没有数据**。R2 是否先做一次 8–12 人盲测再定重排方案，请 Codex 定。
3. **R2 的取舍建议按这个顺序**：先在 1280×720 / 1366×768 / 1920×1080 / 2560×1440 与 100%/125%/150% 缩放下
   记录遮挡与点击问题，再做侧栏重排与开场教学。桌面包已经把窗口尺寸与缩放问题隔离开，
   但**横屏整体重排本轮没有做**（本阶段明确不做），所以桌面版仍然是竖屏 9:16 的构图。
4. **R2 的验收要沿用本轮的取证方式**：真实鼠标键盘 + 截图 + 原始日志，
   不要用「脚本改状态」代替真人操作——本轮 18 战的覆盖就是反例：它证明可达，不证明好玩。
5. **R3 之前先把存档的「检查点粒度」定下来**：如果要存战斗中途快照，
   现在的同步存储接口要改异步，`RUN.save()` 的调用链要一起改（见 9.3）。这件事越晚做代价越大。
6. **R5 之前必须解决签名**，并把本报告第 8 节的内存与冷启动数字在 R5 指定的三档机器上重测一遍。
